Topic 1 — The Mental Model

A Skill Is Just a Folder

Let's cut through the noise. A skill is one folder with one file inside it called SKILL.md.

That file has two parts:

  1. A YAML header ("YAML" = a simple key-value format, like filling out a form) that tells Claude when to use the skill
  2. Markdown instructions that tell Claude how to do the work

That's it. No code. No API keys. No terminal.

Topic 1 — The Mental Model

The Kitchen Analogy

MCP Servers = The Kitchen

A professional kitchen gives Claude access to tools, APIs, and data — the oven, the knives, the pantry. (MCP = Model Context Protocol — a way to connect Claude to external services.)

Skills = The Recipes

Step-by-step instructions on how to create something valuable with those tools. And here's the thing: plenty of amazing dishes don't need a professional kitchen.

Common Trap: "I don't have an MCP server, so skills aren't for me." Nope — Category 1 skills (Document & Asset Creation) work with just Claude's built-in capabilities. No MCP required.

Topic 2 — Folder Structure

Anatomy of a Skill Folder

your-skill-name/
  ├── SKILL.md  ← Required — this IS your skill
  ├── scripts/  ← Optional — executable code
  ├── references/  ← Optional — docs Claude can pull in
  └── assets/  ← Optional — templates, icons, etc.

One folder. One required file. Everything else is optional.

Topic 2 — Folder Structure

Rules That Will Bite You

1. Exact filename

The file must be named exactly SKILL.md

✗ skill.md   SKILL.MD
✓ SKILL.md

2. Kebab-case folders

Kebab-case = words-on-a-skewer

✗ My Cool Skill   my_cool
✓ my-cool-skill

3. No README.md

All docs go in SKILL.md or references/

✗ README.md inside skill
✓ references/guide.md
Topic 2 — Folder Structure

Progressive Disclosure

Claude loads information in layers — only what it needs, when it needs it.

Level 1 YAML Frontmatter (the "nutrition label")
Always loaded. Tiny. Just enough for Claude to decide: "Should I use this skill?"
Level 2 SKILL.md Body
Loaded when the skill triggers. Your main recipe — steps, examples, troubleshooting.
Level 3 references/ Files
Loaded on demand. Detailed docs, API specs, deep examples. Keep SKILL.md under 5,000 words.

Topic 3 — YAML Frontmatter

The 5 Lines That Decide Everything

This is the single most important part of your skill. If your frontmatter (the "nutrition label" at the top of your file) is wrong, Claude will never load your skill. Ever. 

---
name: your-skill-name
description: What it does. Use when user asks to
  [specific phrases]. Key capabilities: [list].
---

Under 1,024 characters. No angle brackets < >. Include the actual phrases users would say.

Topic 3 — YAML Frontmatter

What Even Is YAML?

YAML is just a way to fill out a form with a text file. Each line is a label followed by a colon and a value. That's it.

Paper Form

Name: weekly-report-generator

Description: Creates weekly team status reports...

YAML Version

name: weekly-report-generator
description: Creates weekly team
  status reports...

Same information. Different format. You've been doing this your whole life.

Topic 3 — YAML Frontmatter

The Description Formula

Your description has three ingredients:

What it does
+
When to use it
+
Key capabilities

The "When to use it" part is where you put trigger phrases — the exact words a user might type. Claude matches these phrases to decide if your skill is relevant.

Common Trap: Writing a description that sounds impressive to humans but means nothing to Claude's routing logic. Claude doesn't care about adjectives — it cares about matching phrases.
Topic 3 — YAML Frontmatter

Good vs. Bad Descriptions

✗ Don't write this

description: Helps with projects.

Too vague. Claude has zero idea when to trigger this.

description: Creates sophisticated
  multi-page documentation systems.

Sounds impressive, means nothing. No trigger phrases.

✓ Write this instead

description: Generates weekly
  engineering team status reports
  in markdown. Use when user says
  "weekly report," "status update,"
  "team standup summary," or
  "engineering update."

What it does + When to use it + real trigger phrases users would actually type.

The Recipe Card

After your YAML header, you write the actual instructions. Think of SKILL.md as a recipe card — not a cookbook.

description: [your description]
---

# Your Skill Name

## Instructions
### Step 1: [First Major Step]
Clear explanation of what happens.

## Examples
### Example 1: [Common scenario]
User says: "..."  →  Claude does: ...

## Troubleshooting
### Error: [Common problem]
Cause → Solution
Topic 4 — Writing Instructions

Specific Beats Vague

✗ Vague

"Step 2: Process the data appropriately."

That's not an instruction, that's a wish. Claude doesn't know what "appropriately" means for your workflow.

✓ Specific

"Step 2: Extract all rows where status = 'active' and group by department. Output a markdown table with columns: Department, Count, % of Total."

Claude knows exactly what to do. No guessing.

Topic 4 — Writing Instructions

The New-Team-Member Test

If a new team member on their first day would have to guess what you mean, you haven't been specific enough.

Read each step of your instructions and ask: "Would a smart person who has never seen my workflow know exactly what to do here?"

If the answer is "they'd probably figure it out" — rewrite it. Probably is the enemy of consistently.

Write the actual instructions, not an outline. This is what Claude will follow. Apply the New-Team-Member Test to every step.

Topic 5 — Workflow Patterns

Five Patterns That Work

1. Sequential

Steps in a specific order. Step 1 feeds Step 2 feeds Step 3.

A → B → C → D

2. Multi-MCP Coordination

Workflows spanning multiple services.

Figma → Drive → Linear → Slack

3. Iterative Refinement

Output improves through repeated quality checks.

Draft → Check → Refine ↻

4. Context-Aware Selection

Same outcome, different tools depending on context.

If X → Tool A  |  If Y → Tool B

5. Domain-Specific Intelligence

Specialized knowledge beyond tool access. E.g., compliance checks baked in.

Input → Domain Rules → Validated Output
Topic 5 — Workflow Patterns

Pick Your Pattern

For most non-developer skills, you'll use one of these two:

Sequential

Each step depends on the previous one. Great for processes with a clear start and end.

Example: Customer onboarding — create account → setup payment → send welcome email.

Iterative Refinement

Output gets better through loops. Great for anything where quality matters more than speed.

Example: Report generation — draft → check against criteria → refine → repeat until passing.

Common Trap: Saying "Iterative Refinement" but writing sequential instructions with no quality-check loop. If there's no "check and redo" step, you're actually Sequential. That's fine — just be honest about it.
Your Turn

Match your pattern

Look at the instructions you just wrote. Which pattern do they follow?

  • Are your steps in a fixed order where each depends on the last? → Sequential
  • Is there a "check quality and redo if needed" loop? → Iterative
  • Does the same task route to different tools depending on context? → Context-Aware

Now check: does your SKILL.md actually reflect the pattern you chose? Can you point to the structural element that proves it?

Topic 6 — Testing

If You Don't Test, Nothing Works

You built a skill. You uploaded it. You ask Claude for help and… nothing happens. It never triggers. Now what?

You should have written your test plan before uploading. The most important test is simple: does the skill actually fire when it should?

This is called a triggering test (checking whether Claude recognizes your skill as relevant for a given request).

Topic 6 — Testing

The Trigger Test Plan

✓ Should Trigger (5+ queries)

  • "Help me set up a new ProjectHub workspace"
  • "I need to create a project in ProjectHub"
  • "Initialize a ProjectHub project for Q4 planning"
  • "Set up our team workspace for the new quarter"
  • "Can you make me a ProjectHub project?"

✗ Should NOT Trigger (3+ queries)

  • "What's the weather in San Francisco?"
  • "Help me write Python code"
  • "Create a spreadsheet for tracking expenses"

The hardest test case: a query that's close to your skill's domain but shouldn't trigger. That's the most valuable one.

Topic 6 — Testing

The Debug Trick

After uploading your skill, ask Claude: 

"When would you use the [your-skill-name] skill?"

Claude will quote the description back to you. If what it quotes doesn't match your intent, your description is wrong. Fix it.

Also watch for over-triggering. If your skill loads for irrelevant queries, add negative triggers:
Do NOT use for simple data exploration (use data-viz skill instead).
Your Turn

Write your trigger test plan

Write at least 5 "should trigger" queries and 3 "should NOT trigger" queries for your skill. They must be realistic — things actual users would type.

  • Include the obvious request
  • A paraphrased version
  • A casual version
  • A version using different terminology
  • One that's slightly adjacent but still in scope

Then cross-check: would all five trigger queries match something in your description? If not, update your description.

Topic 7 — Common Mistakes

Three Mistakes Everyone Makes

1

Vague Description

"Helps with projects." Claude has no idea when to trigger this. It's the skill equivalent of a resume that says "hard worker."

2

Stuffing SKILL.md

Dumping your entire API docs into one file. Like reading the entire cookbook before making toast. Use references/ instead.

3

Skipping Tests

You built it, uploaded it, and... nothing happens. It never triggers. You should have written your test plan before uploading.

Topic 7 — Common Mistakes

The Fix Is Always the Same

Vague description

"Helps with projects" tells Claude nothing.

→ Apply the formula: What + When + Capabilities
SKILL.md over 5,000 words

Everything crammed into one file.

→ Move detailed docs to references/
No triggering tests

Uploaded and hoped for the best.

→ Write 5 should + 3 shouldn't queries first

The pattern: every failure comes from being too vague or too lazy to test. Be specific. Verify. Iterate.

Topic 8 — Distribution

Sharing Your Skill

For Personal Use

  1. Create or download the skill folder
  2. Zip it up
  3. Upload to Claude.ai via
    Settings → Capabilities → Skills

Or place it in Claude Code's skills directory if you use the CLI. (Okay, maybe a tiny bit of terminal. But just drag-and-drop.)

For Sharing with Others

  1. Host on GitHub with a clear README (for humans — separate from SKILL.md)
  2. Include example usage & screenshots
  3. Write an installation guide

If you have an MCP server, link your skill from its documentation.

Topic 8 — Distribution

Outcomes, Not Features

When you describe your skill to other people, flip the lens.

✗ Feature-focused

"The ProjectHub skill is a folder containing YAML frontmatter and Markdown instructions that calls our MCP server tools."

This describes what it is. Nobody cares.

✓ Outcome-focused

"The ProjectHub skill enables teams to set up complete project workspaces in seconds — including pages, databases, and templates — instead of spending 30 minutes on manual setup."

This describes what it achieves. That's what people care about.
